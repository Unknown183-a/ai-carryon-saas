Part 0 · Chapter 0.5 — One Platform, Every Customer

Multi-Tenant SaaS Architecture

The single most important structural fact about AI CarryON, stated before any diagram gets specific: there is exactly one of everything below the customer layer.

fig 0.5 — every customer, same platform, isolated at every branchCh.0.5

The Five Questions Every Reviewer Asks

Why do all customers share one backend?

Cost and consistency. A dedicated FastAPI instance, LangGraph deployment, and database stack per customer would mean paying for idle infrastructure for every small channel and re-shipping every bug fix N times. One backend means one deploy (Ch.17) fixes everything, and Cloud Run's scale-to-zero (Ch.17) only makes sense when usage is pooled across many tenants rather than reserved per tenant.

Why is there only one Firebase project?

Firebase Auth and Firestore security rules are designed to isolate at the document level, not the project level — one project with rules keyed on request.auth.uid (Ch.12e) is the intended usage pattern, and it's what lets a single Learning Agent deployment (Ch.20) read across workspaces for platform-level metrics without needing cross-project credentials.

How are users isolated?

By the four-value check chain from Chapter 12e — Workspace ID → Channel ID → Authenticated User ID → Permission Check — enforced before any request reaches Firestore, Redis, or Qdrant. Isolation is a property of every request, not a property of the deployment.

Why can one user never see another user's channels?

Because isolation is enforced redundantly at four layers (Ch.12e's table: FastAPI, Redis, Qdrant, Firestore), not just one. A bug in any single layer's filter still leaves three others standing between one user's request and another user's data.

How does one platform run hundreds or thousands of channels simultaneously?

Because a "channel" is data, not infrastructure. A Channel Brain (Ch.12b) is a namespaced slice of shared Redis and Qdrant plus a Firestore document — creating channel #1,000 costs one Channel Factory run (Ch.12d), not one new server. The Worker Pool (Ch.15) and Cloud Scheduler (Ch.16) already fan out across every channel due to run, bounded only by concurrency limits, not by channel count.

Where to go next This chapter answered why the platform is multi-tenant. Chapters 12b–12e, later in the document, answer how — the exact namespacing scheme, the onboarding flow, the provider-key storage, and the enforcement table. FastAPI Gateway

Every request, from browser click to LangGraph invocation, crosses exactly this line first.

Why FastAPI

The pipeline spends most of its time waiting — on an LLM token stream, a Firestore write, a storage upload. FastAPI's native async def handlers mean one worker process can juggle dozens of in-flight requests instead of blocking a thread per request, and the automatic OpenAPI schema keeps the frontend and backend contracts honest without hand-written docs.

LangGraph Orchestrator

The state machine that owns the entire video-generation run, from the moment FastAPI hands it a job to the moment a video is published.

Node Table

NodeTypeBehavior
TrendStandardPulls topic candidates from Google Trends, cached in Redis (Ch.11).
ResearchStandardRuns the RAG pipeline (Ch.05/09) to build a grounded summary of the chosen topic.

State, Conditional Edges & Retries

LangGraph threads a single mutable state object through every node — it accumulates the topic, the research summary, the planner's JSON, and each parallel agent's output. Edges after Review are conditional: the LLM Judge's verdict decides whether state flows forward to Upload or loops back to Parallel. A per-node retry counter caps re-execution at three attempts before the run is marked failed and handed to the Alert Agent (Ch.19) instead of looping forever.

Sequential nodes

Trend → Research → Planner run strictly in order; each depends on the previous node's output.

Parallel fan-out

The six writer agents share no dependency on each other — LangGraph schedules them concurrently, then joins.

Conditional loop

Review can send state backward exactly once per failure category, never past the retry ceiling.

Parallel Generation

Six agents, one Planner contract, zero dependencies between them — so LangGraph runs them at the same time.

Chapter 09 — Embeddings, Chunking, Retrieval

RAG, In Full

Chapter 5 showed where RAG sits in the pipeline. This chapter opens the box.

Why a Vector Database Instead of SQL

SQL answers "which rows exactly match this filter". RAG needs to answer "which past research, comments, or scripts are semantically closest to this new topic" — a question with no exact-match answer. A vector database indexes meaning, not keywords, using approximate nearest-neighbor search over embeddings.

Chunking

Source documents (articles, past scripts, transcripts) are split into overlapping chunks of roughly 300–500 tokens before embedding. Overlap prevents a sentence that carries the key fact from being cut in half at a chunk boundary.

Metadata

Every chunk is stored with metadata — channel_id, source_type, published_at — so retrieval can filter (only this channel's history) before it ranks by similarity, rather than searching the entire vector space.

Hybrid Search

Pure vector similarity occasionally surfaces a topically-close but factually-irrelevant chunk. The retriever combines vector similarity with a keyword-overlap score, so an exact term match can outrank a vaguer semantic neighbor when both signals matter.

Collections vs. MemoryQdrant is both — a live retrieval index for the current run, and a growing long-term memory the Learning Agent (Ch.20) writes back into. Chapter 10 details every collection.

Chapter 12b — One Isolated Mind Per Channel

Channel Brain

Everything through Chapter 12 described one channel's pipeline. AI CarryON actually runs many channels, for many users, on one shared backend — this is the unit that keeps them from bleeding into each other.

A Channel Brain is not a separate deployment. It's a scoped slice of the same Redis, the same Qdrant, and the same Firestore — every read and write for a channel is automatically filtered to that channel's own data before anything else happens. A cricket channel's research never leaks into a finance channel's suggestions, even though both run through the identical LangGraph engine.

fig 12b.1 — one Channel Brain, eight owned componentsCh.12b
ComponentHolds
Channel DNANiche, region, language, tone, brand voice — the identity that makes this channel distinct from every other.
Prompt LibraryThe channel's own prompt variants for Script, SEO, and Thumbnail, layered on top of the platform's global prompts.
AnalyticsThis channel's rolling performance data only — never mixed with another channel's numbers.
LearningLessons this specific channel's Learning Agent (Ch.20) has distilled from its own history.
Viewer FeedbackComment sentiment and retention signals scoped to this channel's audience.
Competitor MemoryRival channels tracked for this niche specifically — a finance channel's competitors are never shown to a cricket channel.
Redis NamespaceEvery cache key from Chapter 11 is actually prefixed ch:{channel_id}: — one Redis instance, logically many caches.
Qdrant NamespaceEvery point in the nine collections from Chapter 10 carries channel_id in its metadata, so retrieval always filters to one channel before it ranks by similarity.
One engine, many brainsThe LangGraph engine itself (Ch.04) is not duplicated per channel. Each run simply loads the requesting channel's Brain first, injects its DNA into every prompt, and executes the same graph — this is what makes adding channel #50 cost nothing in new infrastructure.

Chapter 12e — What Stops One User From Seeing Another's Data

Tenant Isolation & Security

One backend serves every workspace. This chapter is the guarantee that sharing infrastructure never means sharing data.

fig 12e.1 — every request is checked in this exact orderCh.12e

Four values are resolved on every single request, in the order shown above, before a handler is allowed to touch Firestore, Redis, or Qdrant. The Permission Check at the bottom does one thing only: confirm that the authenticated user's uid is a member of the workspace that owns the requested channel. If that check fails, the request is rejected before any downstream service — including the LangGraph engine — is ever invoked.

The isolation guarantee, stated plainlyA user can only access channels that belong to their own workspace. No user can see another user's channels — not partially, not through a shared cache key, not through a vector search that forgot to filter by channel_id. Every namespace introduced in Chapter 12b exists to make that sentence true at the infrastructure level, not just the application level.

Where isolation is enforced, layer by layer

LayerEnforcement
FastAPIPermission Check middleware runs before any router handler executes.
RedisEvery key is namespaced ch:{channel_id}:* (Ch.12b) — a lookup for the wrong channel simply misses.
QdrantEvery query carries a mandatory channel_id metadata filter before similarity ranking runs.
FirestoreSecurity rules require request.auth.uid to match the workspace's member list on every document read.

Purpose: auth verification and Firestore reads/writes. Dependencies: Firebase Admin SDK. Who imports it: api/middleware/auth.py, channels/. Who calls it: every authenticated request. Input: a JWT or a document path. Output: a verified user or a document snapshot.

redis/

Purpose: a thin namespaced client wrapping get/set/TTL. Dependencies: redis-py. Who imports it: agents/, api/middleware/rate_limit.py, channels/. Who calls it: anything that needs a cache. Input: a channel-scoped key. Output: a cached value or a miss.

channels/

Purpose: Channel Brain model and the Channel Factory automation (Ch.12b–12d). Dependencies: firebase/, redis/, database/. Who imports it: api/routers/channels.py, langgraph/. Who calls it: the create-channel endpoint and every pipeline run's first step. Input: a channel config form. Output: a ready Channel Brain.

monitoring/

Purpose: Health Agent checks and Alert Agent escalation (Ch.18–19). Dependencies: every service client (redis/, firebase/, database/). Who imports it: scheduler/ (periodic health run). Who calls it: Cloud Scheduler, on a timer. Input: nothing — it polls. Output: a health report or an incident.

workers/

Purpose: handlers Cloud Tasks invokes for slow jobs (Ch.15). Dependencies: agents/ (voice, render), firebase/ (storage). Who imports it: nothing — it's an entry point. Who calls it: Cloud Tasks, via HTTP push. Input: a task payload. Output: a completed render, upload, or thumbnail.

scheduler/

Purpose: the job definitions Cloud Scheduler triggers (Ch.16). Dependencies: api/ (calls back into FastAPI), channels/. Who imports it: nothing — it's an entry point. Who calls it: Cloud Scheduler, on a cron expression. Input: none. Output: a new LangGraph run per due channel.

Bird's-Eye› Runtime› Cloud Tasks & Workers
Chapter 15 — Off the Request Thread

Cloud Tasks & Workers

Voice generation, rendering, and uploading are each too slow to hold an HTTP request open for. This is why they run as background jobs instead.

fig 15.1 — fire-and-track, not fire-and-forgetCh.15

Why background jobs are needed: an FFmpeg render can take minutes, and a YouTube upload depends on an external API's own latency — neither belongs inside a synchronous request-response cycle. LangGraph's final node enqueues a Cloud Task instead of doing the work itself, and returns immediately. Cloud Tasks guarantees at-least-once delivery to the worker pool, retrying automatically on a 5xx response, which is what makes the pipeline resilient to a worker crashing mid-render.

Chapter 16 — What Wakes The System Up

Cloud Scheduler

Nothing runs unprompted. Cloud Scheduler is the only component allowed to start a pipeline run without a human clicking anything.

fig 16.1 — Scheduler triggers FastAPI, which starts LangGraph like any other requestCh.16

Cloud Scheduler carries no logic of its own — it fires an HTTP call on a cron expression, and FastAPI treats that call exactly like one from the dashboard, just with a system-issued token instead of a user's JWT. This is why Scheduler-triggered runs pass through the same Permission Check described in Chapter 12e, scoped to a system role rather than a human user.

Bird's-Eye› Runtime› Deployment
Chapter 17 — From Commit to Running Service

Deployment

One path, every time — no manual deploys, no snowflake environments.

fig 17.1 — GitHub → Actions → Docker → Cloud Run → Load Balancer → FastAPI → LangGraph → Redis / Qdrant / FirestoreCh.17

A merge to main triggers GitHub Actions, which builds the Docker image, runs the test suite, and pushes to Cloud Run on success. Cloud Run's built-in load balancer distributes traffic across container instances, scaling to zero when no request has arrived recently — appropriate for a system whose real workload is scheduled, not constant. Redis, Qdrant, and Firestore are deployed and scaled independently of the FastAPI containers, since they hold state that must outlive any single container's lifecycle.

Chapter 18 — Entire Graph, Watched

Monitoring & Health Agent

A second, smaller LangGraph — the Infrastructure LangGraph — whose only job is to ask every other component "are you okay?" on a timer.

fig 18.1 — every dependency this document introduced, polled on one scheduleCh.18

The Health Agent runs as its own small LangGraph, triggered by Cloud Scheduler on a short interval, independent of any user-facing video pipeline. Each check node calls one service's lightest possible endpoint — a Redis PING, a Firestore metadata read, a Qdrant collection count — and records a pass or fail. A single failing check does not by itself page anyone; it hands its result to the Alert Agent, which decides what happens next.

Bird's-Eye› Nervous System› Alert Agent
Chapter 19 — Retry, Then Escalate

Alert Agent

Failure is expected. What matters is that it's never silent and never infinite.

fig 19.1 — Retry ×3 → Alert Agent → Email → Dashboard → Incident Report → Pause SchedulerCh.19

The chain in the diagram is the same retry ceiling introduced back in Chapter 04 — three attempts, then escalation instead of a fourth silent retry. Once escalated, the Alert Agent writes an Incident Report to Firestore and, for failures serious enough to risk repeated bad output (not a single transient timeout), pauses that channel's entry in Cloud Scheduler until a human acknowledges the incident.

Bird's-Eye› Nervous System› Learning Agent
Chapter 20 — Closing the Loop

Learning Agent

The only node whose job is to make every future video slightly better than the last, using nothing but this channel's own history.

fig 20.1 — Analytics → Pattern Detection → Lessons Learned → lessons_learned collection (Ch.10) → future Research/Planner runsCh.20

The Learning Agent runs on a schedule (Ch.16), reading each channel's own Analytics — not another channel's, per the isolation guarantee in Chapter 12e — and looking for statistically-supported patterns: which hooks correlate with higher retention, which SEO angles underperform. Confirmed patterns are written as new points into Qdrant's lessons_learned collection with that channel's channel_id, where the Research and Planner agents will retrieve them on the very next run — closing the loop first opened in Chapter 05.

Bird's-Eye› Growing the System› New Channel
Chapter 21 — The Test of a Good Architecture

Adding a New Channel

This chapter is the payoff for every isolation decision made in Part V. Adding channel #50 should never mean touching the pipeline that already runs 49 others.

A new channel changes exactly six things, all of them data, none of them code:

config.yaml

Identity, schedule, and provider keys from the Channel Factory (Ch.12d).

Prompts

Channel-specific overrides layered on the global Prompt Library (Ch.12b).

Research sources

Which sites and RSS feeds the Research Agent trusts for this niche.

Branding

Logo, color, and thumbnail style baked into the Channel DNA.

SEO keywords

Seed terms the SEO agent expands from, specific to this audience.

Voice & thumbnail settings

The ElevenLabs voice profile and thumbnail template this channel uses.

What stays unchangedThe LangGraph pipeline (Ch.04), every agent's code (Ch.05–08), the review gate (Ch.08), the Redis and Qdrant clients (Ch.11, Ch.10), FastAPI's routers (Ch.03), and the deployment (Ch.17) — none of it is touched. The Channel Factory (Ch.12d) provisions the new Channel Brain, Cloud Scheduler picks it up on its own schedule (Ch.16), and the very next run flows through infrastructure that was already correct.
