## Phase 5 — Qdrant + RAG
*(SAD reference: Chapters 09–10 — RAG Deep Dive, Qdrant)*

**Goal:** the Research Agent from Phase 4 retrieves grounded context from Qdrant instead of raw web search alone.

**Depends on:** Phase 4.

**Tasks:**
- [x] `backend/ai/rag/chunker.py` — 300–500 token chunks with overlap (Ch.09)
- [x] `backend/ai/rag/embed.py` — embedding client
- [x] `backend/ai/rag/retriever.py` — hybrid search (vector similarity + keyword overlap, Ch.09)
- [x] Create the 9 Qdrant collections from Ch.10: `scripts`, `research`, `comments`, `viewer_feedback`, `competitors`, `analytics`, `knowledge`, `prompt_history`, `lessons_learned`
- [x] Wire `backend/ai/agents/research_agent.py` to call the retriever before calling the LLM (fig 5.1's flow)
- [x] Backfill: embed and load a handful of past scripts/research from the *old* pipeline into `scripts` and `research` collections, so retrieval has something to find on day one

**Definition of Done:** a research run returns a summary that visibly cites retrieved chunks, and querying Qdrant directly shows points landing in the correct collection with correct metadata.

**Handoff Notes:**
> **What's built and verified:** `tests/phase5_qdrant_rag_test.py` (everything external faked — no real keys/network needed) proves both halves of the Definition of Done plus the supporting pieces: (1) `ensure_collections()` creates all nine Ch.10 collections and is idempotent; (2) the chunker produces overlapping multi-chunk output for long text and a single chunk for short text; (3) `hybrid_search` ranks an on-topic chunk above a same-collection distractor, AND proves Ch.12e isolation — a different channel's matching-content point never surfaces; (4) a full `research_node` run retrieves a seeded prior-research chunk, the summary visibly contains a `[Retrieved: ...]` citation (the fake LLM only emits that if it was actually handed a non-empty retrieved-context section — this proves the wiring, not just string luck), and a new point lands in the `research` collection afterward with correct `channel_id`/`topic` metadata. All 13 checks pass; Phase 4's test suite was re-run afterward and still passes unchanged.
>
> **Architecture decision — no `qdrant-client` SDK, a thin REST wrapper instead:** `backend/app/core/qdrant_client.py` talks to Qdrant's REST API directly over `httpx`, the same pattern `redis_client.py` already used for Upstash. Two reasons: (1) consistency — this codebase has exactly one pattern for "external stateful service over REST", no reason for a second; (2) testability — every other external REST dependency here is faked via `httpx.MockTransport`, and the fake Qdrant server in the test file (~40 lines) does real cosine-style scoring, real metadata filtering, and real collection existence checks, which would've been messier to fake against the official SDK's internals. No new dependency was added to `requirements.txt` because of this — `httpx` was already there.
>
> **fig 5.1's flow, as actually wired:** `research_agent.py` no longer uses web search *instead of* RAG — it runs both. On a cache miss: web search (Serper) AND hybrid-search retrieval against this channel's `research` and `knowledge` Qdrant collections both feed the LLM's context in the same call, each in its own labeled section, and the prompt (`prompt_library.py`) explicitly asks the LLM to cite any retrieved chunk it draws on as `[Retrieved: <label>]`. After a fresh summary is produced, it's chunked/embedded/upserted right back into `research` (`_write_back` in `research_agent.py`) — so the *next* run on a related topic has it to retrieve. Both the retrieval read and the write-back are best-effort: wrapped in `try/except` that degrades gracefully (falls back to web-search-only grounding, or just skips the write-back) rather than failing the whole run — confirmed for real by re-running Phase 4's test suite, which doesn't fake Qdrant at all, and seeing it still pass cleanly with Qdrant calls quietly no-op'ing.
>
> **Embedding model choice:** `gemini-embedding-2` via `client.models.embed_content`, truncated to `output_dimensionality=768` (not its 3072 default) — one of the model's officially supported Matryoshka sizes, chosen to keep Qdrant storage/search cost down without a meaningful quality hit. This number is now load-bearing: `ai/rag/collections.py`'s `EMBEDDING_DIM` must match it, and changing either without the other means every collection needs re-embedding from scratch. Also load-bearing: `task_type` — `"RETRIEVAL_DOCUMENT"` when embedding text going into Qdrant, `"RETRIEVAL_QUERY"` when embedding a search query (`embed.py`'s `embed_text()` takes this as a parameter; `retriever.py` and `store_chunks()` already pass the right one each). Gemini's embedding space is asymmetric between these two — mixing them up silently degrades retrieval quality rather than erroring, so it's easy to get wrong without noticing. **Not yet verified against the real API** — same gap Phase 4 flagged for Gemini's generate/JSON-mode behavior: this sandbox can't reach `generativelanguage.googleapis.com`, so the exact embedding response shape (`response.embeddings[0].values`) is confirmed against Google's current published docs/examples, not a live call.
>
> **UPDATE 2026-07-24 — caught a second retired-model bug before it hit a real run.** This phase originally defaulted to `gemini-embedding-001`. Checking Google's own deprecation table (prompted by Phase 4's real run catching the exact same failure mode with `gemini-1.5-flash`) showed `gemini-embedding-001`'s official shutdown date was **July 14, 2026 — 11 days before this was checked**, with `gemini-embedding-2` as the documented replacement. Switched the default before anyone burned a real Qdrant-verification session hitting a live 404 the same way Phase 4 did. `gemini-embedding-2`'s response shape and `output_dimensionality=768` support are confirmed against Google's current official docs (same confidence level as before — still not a live call from this sandbox, which still can't reach `generativelanguage.googleapis.com`). **This phase's real-API verification is therefore still fully open** — same three action items as originally listed below, just against the corrected model name.
>
> **UPDATE 2026-07-25 — real Qdrant run found a real bug the faked test couldn't catch.** The repo owner created a real Qdrant Cloud cluster and ran `tests/phase5_real_keys_smoke_test.py`. The real Gemini embedding call succeeded immediately (768-dim vector, confirming `gemini-embedding-2` works and the fix above was correct) and `ensure_collections()` created all nine real collections cleanly. But the very next step — counting points filtered by `channel_id` — failed with a real `400`: `"Index required but not found for \"channel_id\"... Create an index for this key or use a different filter."` Real Qdrant Cloud requires an explicit payload index before a field can be used in a query filter; the faked test server never enforced this, so it couldn't have caught it.
>
> This took **three** attempts to actually fix, and the middle one was a red herring worth understanding so it doesn't happen again:
> 1. **First attempt:** added `create_payload_index()`, called from `ensure_collection()`. Reported success, but the next real run hit the identical error.
> 2. **Second attempt:** assumed an async-indexing race (Qdrant does process index creation asynchronously by default) and added `wait=true`. Reasoned correctly about a real Qdrant behavior, but **still didn't fix it** — because the code path that would have benefited from `wait=true` was never actually being reached at all.
> 3. **Actual root cause, found by fetching `/collections/research` directly and seeing `"payload_schema":{}` — empty, even after both "fixes":** `ai/rag/collections.py`'s `ensure_collections()` had its own `if not client.collection_exists(name)` check *before* ever calling `client.ensure_collection()`. Since all nine collections already existed (from the very first run, before any of this was fixed), that outer check was `False` for every one of them — so `ensure_collection()`, and therefore `create_payload_index()`, never ran at all. The "wait=true" fix was correct in isolation but irrelevant, since the code containing it wasn't executing. **Real fix:** removed the redundant pre-check in `ensure_collections()`; it now calls `client.ensure_collection()` unconditionally for every collection, every call. `ensure_collection()` now returns whether it created a new collection (previously returned `None`), so the caller can still track newly-created collections without needing its own existence check.
>
> **Lesson for whoever debugs something like this again:** when a fix "should" work but the exact same error persists, verify the fixed code path is actually being *reached*, not just that it's logically correct — `/collections/{name}` (Qdrant's own collection-info endpoint, shown in the code comment on `qdrant_client.py`'s docstring) is what finally exposed this, by showing `payload_schema` was empty when it should have shown the index. **Re-run `tests/phase5_real_keys_smoke_test.py` one more time to confirm this actually resolves it** — same caveat as before: don't take a well-reasoned fix on faith, confirm it.
>
> **UPDATE 2026-07-25 (later same day) — confirmed. This phase is now genuinely, fully verified for real.** The third fix worked: `ensure_collections()` ran clean, the `count()` call that had failed three times in a row now succeeded (0 points, no error). The first full pipeline run that followed hit the Redis research cache from an earlier Phase 4 test (same topic, same day, 24h TTL) and correctly skipped RAG retrieval/write-back entirely — expected cache behavior, not a bug, and the test script's own printed message correctly explained this rather than reporting a false failure. Deleted that one cache key and re-ran: real web search, real RAG retrieval, real LLM summarization, and **a real point landed in Qdrant's `research` collection** with correct `channel_id: "ai_carryon"` and `topic: "new AI model release this week"` metadata. Independently fact-checked the new research summary's specific claims afterward (same practice as Phase 4's verification) — "Nano Banana" (Google DeepMind's real, well-documented image-model family), Gemini 3.6 Flash, GPT-5.6 Luna/Sol, Claude Opus 5, Grok 4.5, Kimi K3 all checked out as genuine, current, accurate. Two real runs in a row, everything verified accurate — the Research Agent's real-world grounding is holding up well in practice, not just in theory.
>
> **What's genuinely still open, for real this time:** `backend/ai/rag/backfill.py` hasn't been run against a real export from the old pipeline — low priority, since no such export exists yet to backfill from. And the `[Retrieved: ...]` citation behavior specifically (as opposed to the write-back, which is now confirmed) still hasn't been observed on a real run — the topic that got a fresh write-back this session would need one more real run on the *same* topic to see retrieval actually pull that point back and cite it. Worth doing once, low urgency; the faked test already proves the citation *wiring* works (see the top of these notes), this would just confirm it against real embeddings' actual similarity behavior instead of the fake's exact-match stand-in.
>
> **Hybrid search weighting:** `VECTOR_WEIGHT=0.7` / `KEYWORD_WEIGHT=0.3` in `retriever.py`, with a `OVER_FETCH_MULTIPLIER=4` (pull `limit*4` candidates from Qdrant's vector search before re-ranking, so a strong keyword match with a merely-okay vector score still has a chance to surface). These are reasonable starting defaults, not tuned against real retrieval quality yet — worth revisiting once there's enough real channel history in Qdrant to evaluate against.
>
> **`backend/ai/memory/channel_memory.py`** is the "first retrieval call" that folder's README was waiting on — `get_lessons_learned()`, a thin facade over `hybrid_search` scoped to the `lessons_learned` collection. It's wired to exist and be callable, but nothing calls it yet in this phase (the Learning Agent that would populate `lessons_learned` doesn't exist until Phase 12) — it'll return an empty list on every real call for now, which is correct, not a bug.
>
> **Backfill is a real script, but seeded with illustrative data, not the actual old pipeline's data:** `backend/ai/rag/backfill.py` reads a JSON export (`--seed-file`, shape documented in the module docstring) and writes into `scripts`/`research` via `store_chunks`. `ai/rag/seed_data/sample_backfill.json` ships 3 sample scripts + 2 sample research summaries in the right shape so the write path is exercised, but this sandbox has no access to the actual old SQLite-based pipeline's data (a different repo — see `ai-carryon`, not `ai-carryon-saas`) to export for real. **Before trusting retrieval quality on real channel history, run `backfill.py` against a real export from that old database**, not the sample file.
>
> **Not done, and out of scope for this phase on purpose:** no multi-tenancy beyond the one hardcoded channel (every `store_chunks`/`hybrid_search` call already takes `channel_id` and filters on it — Ch.12e isolation is proven by Test 3 — but there's still only ever one real channel to test with until Phase 6); no Health Agent check for "Qdrant down" (Ch.16's table already describes the expected behavior — "Research Agent falls back to web search only; alert raised" — the fallback half is built and tested here, the alert half is Phase 10's job); the other seven collections (`comments`, `viewer_feedback`, `competitors`, `analytics`, `prompt_history`) are created and ready but nothing writes to them yet — that's later phases' work (Phase 7 workers, Phase 12 Learning Agent, etc.).
>
> **Cost note for the repo owner:** each real research run now makes one additional real API call beyond Phase 4's count — the query embedding for retrieval (cheap, `gemini-embedding-2` is inexpensive per call) — plus one embedding call per ~350-word chunk of the newly-generated summary for the write-back (typically 1-2 chunks for a research summary this length). Still cheap on Gemini's free tier, but no longer literally free of extra calls the way Phase 4's web-search-only path was.
