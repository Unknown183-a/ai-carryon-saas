## Phase 6 — Multi-Tenancy: Channel Brain, Workspace, Channel Factory
*(SAD reference: Chapters 12b–12e — Channel Brain, User Workspace, API Providers, Tenant Isolation)*

**Goal:** the single hardcoded channel from Phase 4 becomes N database-driven channels, each isolated, created through a real onboarding flow.

**Depends on:** Phase 5 (needs Qdrant collections to namespace) and Phase 3 (needs Redis to namespace).

**Tasks:**
- [x] Retrofit Redis keys everywhere to `ch:{channel_id}:*` prefix (Ch.12b) — grep the whole codebase for raw Redis calls, there should be none left unprefixed
- [x] Retrofit every Qdrant write/query to carry mandatory `channel_id` metadata filter (Ch.12b)
- [x] `backend/tenant_platform/channels/brain.py` — the Channel Brain model (DNA, prompt library overrides, per-channel settings)
- [x] `backend/tenant_platform/factory/factory.py` — implements the exact sequence from fig 12d.1: Validate Configuration → Create Firestore Record → Create Redis Namespace → Create Qdrant Namespace → Generate Channel DNA → Channel Ready
- [x] `POST /workspaces` — creates a Workspace document on first login (Ch.12c)
- [x] `POST /channels` (replace the raw Phase 2 version) — now runs through the Channel Factory
- [x] Provider-key storage: encrypt at rest, store per channel, scoped so one channel's agents never see another channel's keys (Ch.12d table)
- [x] `backend/tenant_platform/security/permissions.py` — Permission Check middleware: Workspace ID → Channel ID → Authenticated User ID → Permission Check, in that order (Ch.12e) — wire into every router, not just channels
- [x] Write a negative test: User A's token requesting User B's channel must be rejected at the middleware layer, before touching LangGraph

**Definition of Done:** two different Firebase users can each create a channel, run the Phase 4 pipeline against their own channel independently, and neither can read, list, or trigger the other's channel — verified by an automated test, not manual inspection.

**Handoff Notes:**
> **What's built and verified:** `tests/phase6_multi_tenancy_test.py` (23 checks, everything external faked — no real Firebase project, Redis, Qdrant, or LLM keys needed) proves the Definition of Done directly: User A and User B each independently call `POST /workspaces` → `POST /channels` (through the real Channel Factory) → `POST /channels/{id}/generate` and get their own reviewed pipeline result back; `GET /channels` never cross-leaks between them; and — the important negative test — User B's token against User A's channel gets HTTP 403 with `graph.ainvoke` proven to never have been called (via a tripwire graph object that raises `AssertionError` if invoked), not just a status-code check. An unknown channel_id correctly gets 404, not 403, so "doesn't exist" and "exists but isn't yours" stay distinguishable without leaking which one it is. Phase 4's and Phase 5's test suites were both re-run afterward — Phase 5 passes unchanged; Phase 4 needed one adjustment, see below.
>
> **Renamed `backend/platform/` → `backend/tenant_platform/` — a real bug caught, not a style choice.** The SAD's prose and this phase's own task list call it `platform/`, but `platform` is a Python stdlib module name (`platform.system()`, etc. — used internally by httpx, uvicorn, and others already in `requirements.txt`). This codebase's established convention (every prior phase) puts `backend/` directly on `sys.path`, and under that convention a `backend/platform/__init__.py` becomes a top-level package literally named `platform` that **shadows the stdlib module for the rest of the process** — verified empirically, not assumed: adding that `__init__.py` and running `import platform; platform.system()` throws `AttributeError: module 'platform' has no attribute 'system'`. Renamed the directory, not the design — every module the brief asks for is exactly where it's supposed to be, just under `tenant_platform/`. Full writeup in `backend/tenant_platform/README.md`; `backend/README.md`, the top-level `README.md`, `BUILD_GUIDE.md`, and Phase 10's still-open brief were all updated to the new path — Phase 0's and prior work-reports' historical mentions of `platform/` were deliberately left alone (they're dated records of what was true when written, not living docs).
>
> **The Redis/Qdrant retrofit, concretely:** `redis_client.py` gained `channel_key(channel_id, suffix) -> "ch:{channel_id}:{suffix}"`; `trend_agent.py`, `research_agent.py`, and `embed.py` (which now takes `channel_id` as a required first parameter — propagated through `retriever.py`'s two call sites) all build their cache keys through it. The one deliberate exception: the rate limiter's per-user budget key (`rl:user:{uid}`) — that one protects total API capacity across every route a user hits, including routes with no `channel_id` at all (`GET /channels`, `POST /workspaces`), so it can't be *only* channel-scoped. Ch.12b's own TODO comment (now resolved) specifically asked for a companion per-channel counter so one channel's traffic can't starve another's — `rate_limit.py`'s `RateLimitMiddleware` now checks both the per-user key AND, for any `/channels/{channel_id}/...` route, a `ch:{channel_id}:rl:*` counter alongside it; either tripping returns 429. Qdrant's retrofit turned out to already be complete — Phase 5 built `store_chunks()`/`hybrid_search()` with `channel_id` as a required parameter from the start (raises `ValueError` if metadata lacks it), so there was nothing left to grep for there; Test 3 in Phase 5's own suite already proved cross-channel isolation, and this phase's Test 1 re-confirms the namespacing pattern end-to-end through a real HTTP-triggered pipeline run.
>
> **Channel Brain (`tenant_platform/channels/brain.py`) deliberately holds less than Ch.12b's full eight-item list.** Ch.12b describes a Channel Brain as holding Channel DNA, Prompt Library overrides, Analytics, Learning, Viewer Feedback, Competitor Memory, Redis Namespace, and Qdrant Namespace. The last two aren't fields on the dataclass — they're conventions enforced by `channel_key()`/`channel_filter()` everywhere else, not data to carry around. Analytics/Learning/Viewer Feedback/Competitor Memory are Qdrant collections (Ch.10) that already exist and are already per-channel by construction (every point carries `channel_id`) the moment a later phase starts writing to them — nothing in `ChannelBrain` needs to change when that happens. What the class actually holds — DNA and prompt overrides — is what's real, queryable Firestore data today. `to_pipeline_config()` returns a dict shape-compatible with Phase 4's `HARDCODED_CHANNEL`, so every existing agent and prompt kept working unchanged against a database-driven channel.
>
> **Channel Factory's "Create Redis/Qdrant Namespace" steps are real but intentionally lightweight** — documented in `factory.py`'s own docstring in detail, summarized here: neither service has an actual "create a namespace" API to call, since namespacing here is a key-prefix/metadata-filter convention, not a provisioned resource. Redis gets one housekeeping marker key (`ch:{channel_id}:_namespace_created_at` — Test 1 checks for exactly this key); Qdrant gets `ensure_collections()` called idempotently (normally a no-op, since Phase 5 already ran it at FastAPI startup). This isn't a shortcut around the brief — it's what those two steps actually *are*, honestly stated instead of manufacturing fake provisioning work to look busier.
>
> **Provider-key encryption** (`tenant_platform/security/provider_keys.py`) uses `cryptography`'s `Fernet` with one platform-wide key (`CHANNEL_SECRETS_ENCRYPTION_KEY`, new in `.env.example`) — not a per-channel key. That's a deliberate scope tradeoff: what Ch.12d's isolation guarantee actually requires is that each channel's *row* in Firestore only ever decrypts to that channel's own values (true here — keys are stored per-channel-id in the `channel_provider_keys` collection), not that the encryption key itself is partitioned. Per-channel KMS-style key management is a bigger system this project doesn't need at this scale yet. Test 1 confirms a submitted `gemini_api_key` round-trips through storage as something other than the plaintext.
>
> **Permission Check (`tenant_platform/security/permissions.py`)'s `require_channel_access`** is a FastAPI dependency, not middleware — Ch.12e's prose says "middleware," but a dependency runs at the same point in the request lifecycle (before the route handler body) for any route that declares it, and gets the huge advantage of being able to `Depends()` on `get_current_user`/`get_firestore` the same way every other auth-aware route already does, instead of re-implementing JWT verification and Firestore access inside raw ASGI middleware. Wired into `POST /channels/{channel_id}/generate` this phase, since that's the only channel-scoped route that exists yet; any future channel-scoped route (upload trigger, per-channel settings, etc.) adds it the same one-line way.
>
> **Phase 4's test needed a real adjustment, not a shim.** `phase4_langgraph_test.py`'s Test 1 originally drove the pipeline through `POST /channels/ai_carryon/generate` over HTTP — that route's behavior legitimately changed this phase (multi-tenant routing replaced the hardcoded single-channel shortcut, by design), so the old HTTP call now 422s on a missing dependency-injected `Request` in a *different* way than before, and asserting against superseded behavior isn't a meaningful regression check anymore. Fixed by having Test 1 call the LangGraph engine directly (`graph.ainvoke()`), exactly the way Test 2 already did — still proves the pipeline itself produces a correct reviewed result, just no longer conflates that with "and the old hardcoded HTTP route still exists," which was never this phase's job to keep true. This phase's own Test 1 now re-proves the HTTP-layer happy path through the *current* endpoint.
>
> **Not done at the time this phase was built, and out of scope on purpose:** No Cloud Function triggers `POST /workspaces` automatically on email verification (Ch.12c describes it that way); it's a plain endpoint the frontend is expected to call once after login instead — documented as a pragmatic substitution in the router's own docstring, not hidden. `llm_client.py`'s existing TODO about honoring a channel's `preferred_model` over the hardcoded `DEFAULT_MODELS` dict is still open — `ChannelBrain.to_pipeline_config()` carries `preferred_model` in its output DNA dict, but no agent reads it yet; every agent still calls `DEFAULT_MODELS[...]` directly. Left alone deliberately: not in this phase's checklist, and wiring it changes every agent's call site, which deserves its own focused pass rather than a drive-by edit here. Frontend, Cloud Scheduler, and monitoring registration (fig 12d.1's last two steps) don't exist yet — Phases 8/10/11's jobs.
>
> **UPDATE 2026-07-25 — real Firebase/Firestore verification complete.** The line above about "no real Firebase project, Firestore, Redis, or Qdrant was exercised" is now out of date — the repo owner ran `tests/phase6_real_keys_smoke_test.py` for real: two real Firebase Auth users, real ID tokens (custom-token → `signInWithCustomToken` exchange), driving the real FastAPI app with `get_current_user`'s actual JWT verification running (no dependency override). Every isolation guarantee this phase's Definition of Done requires held up for real: independent workspaces, independent channels, `GET /channels` never cross-leaking, User B's token against User A's channel correctly getting 403, an unknown `channel_id` correctly getting 404 not 403. The multi-tenancy logic itself had zero bugs.
>
> What the real run *did* surface — twice — were two pre-existing over-strictness bugs in Phase 4's Review Agent prompts, unrelated to this phase's own isolation logic but only visible once real content ran through real review checks at volume: the Grammar Check was failing grammatically correct writing over style preferences (word choice, active/passive voice), and the Copyright Check was flagging a script and its own description as "copying" each other for sharing the same topic — both fixed in `prompt_library.py` (full detail in `phases/phase-04-langgraph-core-agents/PHASE.md`'s handoff notes, since that's where these prompts live). After both fixes, a follow-up real run passed clean on the first try — all four review gates green, zero retries needed. This phase's own isolation guarantees were never in question at any point; the retries were entirely a content-quality-check calibration issue in a different phase's code.
