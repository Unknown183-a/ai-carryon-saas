# Milestone — Phase 3 Complete

**Date:** 2026-07-23
**Phase:** Phase 3 — Redis (Upstash)

## What shipped

- `backend/app/core/redis_client.py` — Upstash REST-backed `RedisClient` (`get`/`set`/`incr`/`expire`/`ttl`/`delete`) with a shared `get_redis()` accessor.
- `backend/app/api/middleware/rate_limit.py` — the Phase 2 stub is now a real fixed-window rate limiter: `rl:*` keys, 60s TTL, `429` + `Retry-After` once the per-minute budget (default 30, overridable via `RATE_LIMIT_REQUESTS_PER_MINUTE`) is spent. Keyed by Firebase uid when available, IP otherwise, so unauthenticated routes are covered too.
- Wired into `backend/app/api/main.py`.
- `backend/requirements.txt` added (first one in the repo).
- `tests/phase3_redis_ratelimit_test.py` — proves the Definition of Done against a fake in-memory Upstash REST server.

## Definition of Done — verified

Per `BUILD_GUIDE.md`: *"hammering the `/health` endpoint past the rate limit returns `429`; waiting past the TTL resets it."*

- [x] Requests within budget succeed
- [x] The request that crosses the budget gets `429` with a `Retry-After` header
- [x] Further requests inside the same window stay `429`
- [x] Forcing the TTL to expire resets the window and requests succeed again

Verified via `tests/phase3_redis_ratelimit_test.py` — see that file's output in `work-reports/daily/2026-07-23-phase3-redis-upstash-done.md`.

## Decisions made along the way

- REST client over `redis-py`/TCP, per the phase brief's explicit "Upstash REST client" wording.
- Rate limiter identity uses an unverified JWT decode rather than a second full Firebase verification per request — `get_current_user` already does the real verification for protected routes.
- `ch:{channel_id}:*` namespacing deliberately left as TODO comments — that's Phase 6's job.
